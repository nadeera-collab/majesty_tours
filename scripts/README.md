# scripts/

Two scripts. Only one of them runs on deploy.

## `build-pages.mjs`: runs on every Netlify deploy

`netlify.toml` sets `command = "node scripts/build-pages.mjs"`. It reads
`content.json` and writes:

- `tours/<slug>/index.html`: the seven multi-day tours
- `tours/index.html`: the hub listing every product
- `day-trips/<slug>/index.html`, `experiences/<slug>/index.html`
- `tours/<slug>/index.html` for the combination tours, whose itinerary,
  gallery and inclusions are **composed from their component tours**.
  Edit a component tour and every combination that uses it updates
- `sitemap.xml`

It has no dependencies and must stay that way: there is deliberately no
`package.json` in the repo, so Netlify runs plain `node` with nothing to
install.

Run it locally after any `content.json` edit:

```bash
node scripts/build-pages.mjs
```

## `optimize-images.mjs`: run by hand, output is committed

The source photos in `assets/` are full-size camera and WhatsApp JPEGs
(~1280px, 100–330KB each). Pages show them as ~190px grid tiles, so
serving the originals meant the 19-photo Grand Island page pulled ~3.6MB
of images to render about 0.05MB worth of pixels.

This script writes width-limited WebP derivatives to `assets/opt/` and
records every photo's intrinsic size in `assets/image-manifest.json`.
`build-pages.mjs` reads that manifest to emit `<picture>` markup with a
correct `srcset` and correct `width`/`height`.

Both the derivatives and the manifest are committed, which is what keeps
the deploy build dependency-free. It needs `sharp`, which is **not** a
project dependency. Install it anywhere and point the script at it:

```bash
npm install sharp
node scripts/optimize-images.mjs
```

If sharp lives somewhere else, set `SHARP_PATH` to the `node_modules`
directory holding it:

```bash
SHARP_PATH=/path/to/node_modules node scripts/optimize-images.mjs
```

Re-running is cheap: it skips derivatives that are newer than their
source. Pass `--force` to re-encode everything.

### When you add or replace a photo

1. Drop the file in `assets/` (or let the CMS upload it there).
2. Point `content.json` at it, via the CMS or by hand.
3. `node scripts/optimize-images.mjs`: generates the derivatives.
4. `node scripts/build-pages.mjs`: regenerates the pages.
5. Commit `assets/<photo>`, `assets/opt/*`, `assets/image-manifest.json`
   and the regenerated HTML together.

If step 3 is skipped the page still works, because `picture()` falls
back to a plain `<img>` pointing at the original. It is just heavy again.

### A note on the homepage

The homepage (`index.html`) is hand-maintained and is **not** generated
by these scripts. It carries its own copy of the tour data in an inline
`window.CONTENT_DATA` blob as a `file://` and fetch-failure fallback; if
you change `content.json`'s `tours` array, that blob has to be
regenerated by hand. The day-trip, experience and combination data added
for the landing pages is deliberately left out of that blob, because the
homepage does not read it.
